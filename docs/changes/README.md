# 变更记录规范

## 1. 目的

`docs/changes/` 记录仓库每一次功能、修复、重构、依赖与配置调整的**发生过程**：改了什么、为什么改、怎么改、影响哪些文件。

它有两个读者：

- 人和 Agent 需要快速回溯“现在这个行为是怎么变成这样的”。
- 下一次改动的执行者需要在动手前知道历史取舍和踩过的坑。

三层文档分工，互不替代：

| 文档 | 回答的问题 | 更新时机 |
| --- | --- | --- |
| `docs/changes/` | **过去发生了什么、为什么** | 每次改动 |
| `docs/modules/<模块>/<主题>.md` | **某个模块内部怎么运转**：状态流、时序、约束、调试入口 | 结论变化时 |
| `AGENTS.md`（根与子项目） | **现在是什么样**：架构、目录职责、开发约定、验证要求 | 架构或约定变化时 |

## 2. 什么时候必须写

以下任一情况，必须与代码在同一次改动中新增一条记录：

- 新增或修改功能行为、交互、接口、数据结构、配置项。
- 修复缺陷，尤其是有根因分析的缺陷。
- 重构、调整模块边界、更换依赖或依赖版本。
- 修改构建、发布、测试、日志等工程链路。
- 修改 `AGENTS.md` 或 `docs/modules/` 中描述的架构结论（记录里说明“为什么改结论”）。

纯格式化、拼写修正、注释微调可以不写。

## 3. 目录与命名

```text
docs/changes/
├── README.md          # 本规范
├── INDEX.md           # 全局索引，新记录插入表格最上方
├── web/               # 前端
├── server/            # 服务端
├── hls/               # C++ 原生扩展
├── desktop/           # 桌面端
└── shared/            # 共享契约、类型、根级脚本与构建
```

- 文件名：`YYYY-MM-DD-<kebab 简述>.md`，日期取改动完成日。
- 一个功能一条记录，不按文件拆分，也不把不相关改动塞进同一条。
- 跨模块改动放入**主导模块**目录，在“涉及模块”中列出全部模块，并在 `INDEX.md` 对应行标注。
- 记录写入后不回改结论；后续再变化就新增记录。确有事实错误时在文末追加 `## 后续修正` 段落并注明日期。

## 4. 记录模板

```md
# <标题>

- 日期：YYYY-MM-DD
- 模块：web / server / hls / desktop / shared
- 类型：功能 / 修复 / 重构 / 依赖 / 文档
- 涉及模块：（跨模块时列出）

## 背景

问题现象、触发条件、为什么要做。

## 目标与取舍

要达到什么效果；考虑过哪些方案，为什么选当前方案。

## 涉及文件

| 文件 | 改动 | 原因 |
| --- | --- | --- |
| `web/src/...` | ... | ... |

## 实现要点

关键数据流、状态变化、边界与失败处理。写“为什么这样做”，不写逐行解释。

## 行为变化与兼容性

对外表现、接口、持久化数据、旧数据的处理方式。

## 验证

执行的命令与手工验证项；未验证的项必须写明原因。

## 关联文档

- `AGENTS.md` 的具体章节
- `docs/modules/...`
```

## 5. 索引维护

`docs/changes/INDEX.md` 是唯一入口，按时间倒序一行一条：日期、模块、类型、标题、主要文件、记录链接。

新增记录必须同时更新索引，禁止只写记录不写索引。

## 6. 何时拆出模块文档

`AGENTS.md` 描述的是全局约定与边界；当某个子功能的实现细节超过约 40 行，或包含状态机、时序、并发、缓存、失败恢复等需要单独演进的内容时：

1. 在 `docs/modules/<模块>/<主题>.md` 新建文档；
2. 在对应 `AGENTS.md` 章节留一行链接，不把细节复制两份；
3. 模块文档只写**当前有效**的结论，变更过程留在 `docs/changes/`。

模块文档目录与维护规则见 `docs/modules/README.md`。

## 7. 提交要求

- **分批提交**：一次提交只做一件事。规范/文档、单个功能、缺陷修复、依赖升级分别提交，不把多个不相关改动压成一个大提交，也不把一个功能拆成“代码一个提交、文档一个提交”。
- **及时提交**：完成一处可验证的改动就立刻提交，不要攒着多次改动最后一起提交。
- **一个功能的提交内容**：代码 + 对应 `docs/changes/` 记录 + `INDEX.md` 行 + 需要同步的 `AGENTS.md` 或 `docs/modules/` 更新，必须落在同一个提交里。
- **提交说明使用中文**，遵循根 `AGENTS.md` 的 Git 提交说明规范：直接描述改了什么，不加英文类型前缀，不使用无意义占位文字。
- 提交前完成对应子项目的验证命令；未验证项写入变更记录的“验证”段落后再提交。

## 8. Agent 阅读顺序

1. 根 `AGENTS.md`；
2. 目标子项目的 `AGENTS.md`；
3. `docs/modules/<模块>/` 下与该功能相关的文档；
4. `docs/changes/INDEX.md` 中近期相关记录（按标题关键词检索）；
5. 动手前确认是否存在“不要再这样做”的历史结论。

## 9. 质量红线

- 必须写清原因；只写“修改了 X”视为不合格。
- 单条记录聚焦一个功能，超过约 150 行说明该拆分或该压缩。
- 不记录临时调试过程、一次性命令输出、密钥、易腐路径。
- 引用代码写文件路径加函数名或行号，不粘贴大段源码。
- 记录中的事实必须与最终代码一致；改动被回退时补一条新记录，不删旧记录。
