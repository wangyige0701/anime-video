# 开发规范新增批次提交时机强制要求

- 日期：2026-11-22
- 模块：shared
- 类型：文档
- 涉及模块：shared（根约定）、web

## 背景

原有约定已经写明「改动必须分批提交」「完成一处可验证的改动后立即提交」，但只有一句原则，没有可执行的顺序和边界。实际执行时仍然出现整批功能、文档和缺陷修复堆到会话末尾的情况：中间状态没有可回滚的检查点，出问题时只能整体回退，提交说明也难以按功能讲清楚。

## 目标与取舍

把「每一批次的功能修改完成后立即提交」升级为强制条款，并补上批次定义、固定执行顺序和无法提交时的处理方式，让规则可以直接被检查，而不是靠自觉理解。

取舍：不引入提交钩子或脚本强制拦截。当前仓库提交频率低、参与者少，钩子会与 `git diff --check`、格式化时机重叠，反而增加出错面；先把顺序写进 `AGENTS.md`，由每次改动自检遵守。

## 实现要点

- 批次定义为一次可独立验证的改动单元：一个功能点、一处缺陷修复、一组规范文档或一次依赖升级。
- 顺序固定为：改代码 → 格式化 → 类型检查 → 受影响测试与 `git diff --check` → 写变更记录并更新 `INDEX.md` → 提交。
- 验证未通过不得提交，禁止「先提交代码、之后补测试或补文档」。
- 当前批次提交前不得开始下一批次；多批次不得积攒到用户提醒或会话结束时统一提交。
- 无法提交时必须当场说明原因与未提交文件范围，不得默认拖延。
- 提交完成后向用户报告提交哈希与提交说明。

## 行为变化与兼容性

仅文档约定，不改变代码、构建流程或既有提交历史。已有提交不受影响，后续批次按新顺序执行。

## 验证

- 通读 `AGENTS.md`「Git 提交说明规范」与「测试用例要求（强制）」两节，确认「一次提交只做一件事」「代码与文档同批提交」「提交前跑测试」三条要求没有互相冲突或重复定义。
- 按新规则立即执行一次：本批规范改动（`AGENTS.md`、`web/AGENTS.md`、变更记录、`INDEX.md`）作为独立提交落地，提交后 `git status --short` 应只剩尚未处理的功能改动。
- `git log -1 --stat` 确认提交说明为中文、范围只包含文档与索引。
