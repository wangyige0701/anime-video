# 模块文档规范

## 1. 定位

`docs/modules/` 保存**当前有效**的模块内部细节：状态流、调用时序、并发与缓存边界、失败恢复、调试入口、关键不变量。

它与其它文档的区别：

- `AGENTS.md`：跨模块的边界与约定，篇幅有限，只写必须让所有人知道的规则。
- `docs/modules/`：单个模块或子功能内部的“指挥手册”，可以写得更细，随实现一起演进。
- `docs/changes/`：一次改动的历史流水，只增不改。

## 2. 目录结构

```text
docs/modules/
├── README.md              # 本规范与模块地图
├── web/
│   ├── detail-episode-sort.md
│   ├── detail-season-sort.md
│   └── ...
├── server/
├── hls/
└── desktop/
```

- 目录与仓库子项目一一对应；跨项目共享契约写 `shared/`。
- 文件名使用 kebab-case 描述子功能，不带日期，例如 `detail-episode-sort.md`。

## 3. 什么时候新建

满足任一条件就新建，而不是继续往 `AGENTS.md` 里堆：

- 子功能实现细节预计超过 40 行说明；
- 存在状态机、异步时序、竞态处理、缓存或资源释放需要单独讲清；
- 需要给出调试入口、已知限制、扩展点；
- `AGENTS.md` 对应章节已明显超出“约定”的粒度。

新建后必须在对应 `AGENTS.md` 章节留下链接与一句话摘要，禁止两处重复维护同一段细节。

## 4. 文档结构

每份模块文档至少包含：

1. **职责边界**：这个子功能负责什么、不负责什么；
2. **状态与数据流**：谁持有状态、如何变化、失败如何回滚；
3. **关键约束**：不能破坏的不变量、性能与并发限制；
4. **扩展点与已知限制**；
5. **验证方式**：如何手工复现与检查。

## 5. 维护规则

- 文档描述“现在”，实现变化时**直接改写**对应段落，不做日期堆叠。
- 实现删除或替换后，必须删掉过时结论，不允许保留冲突描述。
- 每次改动涉及模块细节时，先更新模块文档，再补 `docs/changes/` 记录。
- 单文件超过约 300 行时按主题拆分，并在两处互相链接。
