# Bangumi 数据同步

## 职责边界

本模块负责把 Bangumi 的元数据与本地视频目录整合：

- 从 Bangumi 搜索条目、读详情与剧集列表；
- 用规则（必要时用模型）把「本地季目录 → 条目」「本地文件 → 官方剧集」对应起来；
- 把系列字段、季标题、集标题与集顺序写入 `.video.json`。

不负责：数据层的扫描与持久化（见 `server/AGENTS.md` 的「系列、季、集数据层」）、前端的展示与确认（见 `web/AGENTS.md` 的「详情页 Bangumi 同步」）。

代码在 `server/src/integrations/`：

| 文件                   | 职责                                                       |
| ---------------------- | ---------------------------------------------------------- |
| `http.ts`              | 最小 JSON 客户端：CONNECT 隧道、超时、429/5xx 退避重试     |
| `bangumi/config.ts`    | 从用户设置解析 Bangumi 请求参数（地址、UA、代理、超时）    |
| `bangumi/client.ts`    | 搜索、条目详情、剧集分页                                   |
| `bangumi/filenames.ts` | 文件名集号解析、特别篇标记、自然排序                       |
| `bangumi/align.ts`     | 官方剧集归一化与「文件 ↔ 官方集」的规则对齐                |
| `bangumi/prompts.ts`   | 季映射与集对齐的提示词契约与结果校验                       |
| `bangumi/tags.ts`      | 标签到系列类型的映射（规则命中 → 剩余交模型）              |
| `bangumi/sync.ts`      | 三段流程的编排、预览构建、写入                             |
| `ai/config.ts`         | 从用户设置解析 AI 请求参数（地址、密钥、模型、代理、超时） |
| `ai/client.ts`         | OpenAI 兼容的 JSON 客户端（兼容性降级）                    |

Bangumi 与 AI 是两个独立模块，互不引用；只共用 `http.ts`，配置各自从 `src/settings/store.ts` 读取。

## 配置来源

两个模块都只读**用户设置**（`settings.json`，位于应用数据目录——与目录白名单同规则：桌面端是系统用户目录，开发态是服务目录，由设置页维护），`config.yaml` 与 `.env` 不再参与：

- 解析是纯函数：`resolveBangumiConfig(settings.bangumi)` / `resolveAiConfig(settings.ai)`，字符串 trim、地址去尾部斜杠、非法超时回退默认值；`getBangumiConfig()` / `getAiConfig()` 只是「读设置再解析」的薄封装。
- 这里**不自建缓存**：`readSettings()` 已持有进程内快照并在写入后更新，多一层缓存只会制造「设置页改完不生效」的问题。
- 未配置时客户端直接抛 503 并提示去设置页填写，不发出必然失败的请求（AI 缺地址/密钥/模型任一项，Bangumi 缺地址）。
- 旧 `.env` 里的 `AI_*` / `BANGUMI_*` / `BGM_*` 可用 `pnpm --filter server exec tsx ../scripts/migrate-env.ts` 一次性写入 `settings.json`，脚本只补空字段，不覆盖设置页里已有的值。
- 两个代理互相独立，不做继承：Bangumi 的代理只作用于 Bangumi 请求，AI 的代理只作用于 AI 请求。

## Bangumi 数据模型

剧集只有三个字段有用，含义容易混淆：

| 字段   | 含义                                                              | 是否落库                       |
| ------ | ----------------------------------------------------------------- | ------------------------------ |
| `type` | 0 本篇（含第 0 话）、1 特别篇、2 OP、3 ED、4 PV/CM、5 MAD、6 其他 | 只用于分类                     |
| `sort` | 播出顺序号，可跨条目连续，可为 0 或小数                           | 否（仅 `officialSort` 供核对） |
| `ep`   | 条目内 1-based 序号，跨条目重复，SP 恒为 0                        | **完全不用**                   |

因此：

- 排序键必须是 `(partIndex, sort)`，`type` 只保留 0/1；`type=4` 的 PV 也可能是 `sort=0`，混进来会与「第 0 话」抢同一个位置。
- 项目内的 `sort` 是 1..N 的连续位置号，不承载「第几集」语义，写入统一走 `Season.rewriteEpisodeOrder(ids)`。

## 三段接口

| 方法 | 路径                                     | 作用                                     | 写库 |
| ---- | ---------------------------------------- | ---------------------------------------- | ---- |
| POST | `/data/series/:seriesId/bangumi/match`   | 搜索 + 模型季映射，返回候选与建议        | 否   |
| POST | `/data/series/:seriesId/bangumi/preview` | 按确认的映射拉详情与剧集，生成 changeSet | 否   |
| POST | `/data/series/:seriesId/bangumi/apply`   | 校验后写入系列字段、季标题、集标题与顺序 | 是   |

`BangumiController` 只做「取实体 → 调编排 → 记日志」，参数模式在 `src/schema/bangumi-sync.ts`（`preview` 每季最多三个条目、`apply` 的排序数组形状），归属校验在编排层（需要读数据层）。

**同步范围是合并组，不是单个系列。** 详情页把主系列与被合并系列的季拼在一起展示，同步必须覆盖同一范围，否则成员的季永远拿不到标题与排序：

- `BangumiController.mergeGroup()` 按主系列的 `mergedIds` 取成员（悬空 id 跳过）；
- `readLocalSeasons()` 遍历整组，成员季的 `path` 加「系列名 / 季目录名」前缀——两组都可能有叫「正片」的季目录；
- `runMatch()` 额外接收成员标题参与搜索关键词（续作常是另一个名字）；
- `applyChangeSet()` 接收整组，按 `seasonId` 跨系列查找季，系列字段（标题/简介/日期/状态/类型）仍只写主系列，保存时等整组落盘。

## 顺序基准

**顺序只由本地文件名决定**，官方数据只提供标题与对应关系。

1. `parseEpisodeNumber()` 按可靠性从高到低解析集号：`SxxEyy` → 「第 N 话」→ 方括号/圆括号编号 → ` - N` → 前缀编号；分辨率、编码、音轨、年份、CRC 会被过滤。
2. **解析出的编号只用于排序和给模型当提示，不代表官方集号。** 磁力原名（`[组名] 作品名 - 05 [1080p][AVC]`）里的数字属于发布组习惯；`00-特别篇.mp4` 的 00 也可能只是编号习惯。归属判定不在规则层做（见下节）。
3. `orderLocalFiles()`：有集号的按集号升序（0 在最前），无集号的按自然序追加到末尾。**不能用字符串排序**：`[Studio GreenTea] ... S3 [09]` 会排到 `01.mp4` 之前，混排目录整季错位。
4. 无集号的文件不插入正片中间：位置无法从名字确定，交人工处理。

## 确证式对齐

`alignByRules()` **只做确证，不做推断**。三条同时满足才给归属：文件名不带特别篇标记、集号能从文件名解析、集号在官方正片 `sort` 里唯一存在。

1. 文件名带「特别篇 / SP / OVA / OAD / 番外」→ 该文件不归规则，记入原因；
2. 集号解析不出 → 记入原因；
3. 同号文件互相排斥，两个都不认（无法判断哪一个是真正的第 N 集）；
4. 集号不在官方正片里 → 记入原因（可能是特别篇、合并集，或编号体系不同）。

四条都通过才 `resolved: true`。任一条命中即 `resolved: false`，由模型接手；但 `assignments` 仍保留**已确证**的文件，模型不可用时不会被清空——预览里这些文件照常显示官方标题，其余标为「未匹配」等人工确认。

特别篇完全不参与规则匹配（官方有、本地也可能有，归属需要语义判断），只在 `notes` 里提示数量。

`resolved: false` 时 `runPreview()` 才调一次模型，且只传该季的文件与官方集。模型返回的映射仍要经过双射校验（每个文件一条、每条官方集最多用一次），**顺序继续取自本地文件名**——提示词里明确要求模型只做对应关系、不参与决定顺序。模型调用失败不影响整季：捕获后写入 warning，退回规则已确证的部分。

官方有、本地没有的集只写入 `missing` 供前端提示，不阻断对齐（用户没下载是正常状态）。`missing` 按**最终采用的**对应关系重算：AI 生效时不能沿用规则阶段的结论。

### 合并集（一个文件装了几集）

本地常见 `01-03.mp4` 这种把连续几集压成一个文件的命名。**是否需要合并、合并成什么标题，都交给模型判断**，后端不写任何规则：

- **触发条件**：规则无法确证，或本地文件数少于官方正片集数（合并必然让文件数变少）。两者都不成立时才对合并额外花一次请求。
- **提示词**：`map` 的值允许是 k 键数组，表示这个文件覆盖了连续几集；模型同时在 `titles` 里给出合并标题（保留各集要点、重复作品名只留一次、用「／」连接、不编造、≤80 字）。第 6 条明确「拿不准就按单集处理并写进 reason」，避免模型强行合并。
- **后端只做校验**：数组里每一项都必须是合法且未被占用的官方集，标题非空且不超长；不合格时告警，标题退回该文件的首集标题。
- **人工审核**：预览里给该行标「合并 N 集」，标题与覆盖集数都参与 diff，用户勾选后才会写入；未勾选即保持当前标题。
- **落库语义不变**：本地仍是一个文件一条集记录，`position` 按文件顺序，覆盖的官方集只用于取标题，不改变排序。

## 预览与写入

- `preview` 的季内条目顺序按条目首播日期升序决定 `partIndex`，不使用前端传入顺序：split cour 的两个条目顺序错了，官方集序列会整体错位。
- 系列字段（标题/描述/日期/状态/类型）直接取接口，不经模型；只有标签 → 类型需要整合：先按同名精确匹配，剩余交模型，避免把制作公司名塞成类型。
- 状态由官方剧集的 `airdate` 推导：首播在未来 → 4，仍有未播 → 2，全部已播 → 3，没有日期 → 0（不猜）。
- `apply` 把入参当作不可信输入：排序数组必须是该季全部集的一个排列（`validateOrder` 校验长度/重复/归属）、季与集必须属于该 series、类型必须落在 `seriesTypes` 范围、状态必须是可写状态。任一失败整次抛错，不做部分写入；写完后统一 `waitDataSave()`。
- 集标题与集类型（`kind`）在同一个循环里写：`episodes[].kind` 有值时才调用 `updateKind()`，缺省表示保持用户当前设置，不会被批量同步覆盖。详见 `docs/modules/web/detail-episode-kind.md`。

## 错误与日志

- 上游 HTTP 非 2xx 由各 `client.ts` 的 `upstreamError()` 抛 502；拿到响应之前的失败（超时、代理不可用、DNS）由 `http.ts` 的 `toUpstreamError()` 转成 504 / 502，并把主机名写进消息——**不能让它回落成 500**：Koa 只处理 `ApiError`，其余异常没有 message，前端只能看到「请求失败」。
- 配置缺失抛 503（例如未配置 AI）。
- 所有状态码通过 `Status` 枚举引用，不写字面量。
- 日志用结构化字段：`series.bangumi.matched` / `previewed` / `applied`，只记 seriesId、季数、候选数、写入字段，不记提示词与密钥。
